PostgreSQL 分区表的原理、实践与 MySQL 对比

记录 AI 调用日志时，我关心两个操作：按时间统计失败率，以及清理超过保留期限的历史记录。每天百万级的写入让这两个操作值得提前设计，但仅凭每天的行数，不能判断单表已经不可用，更不能推导出分区后查询一定更快。

这篇文章围绕 ai_call_record 的时间范围查询和生命周期管理展开。SQL 以 PostgreSQL 17 为目标；MySQL 部分参照 8.4 文档讨论功能约束。文中提供的是机制验证方法，不是两种数据库的性能排名。

先从查询和保留周期决定分区键

对于调用日志，可以先列出访问方式，再决定是否按天分区：

访问方式 按 started_at 分区的意义 还需要处理的问题
统计最近一天各渠道的失败数 查询条件能限定时间范围 单日内的过滤、聚合仍有成本
排查某次调用 如果同时知道时间，能缩小范围 只有 call_id 时仍需考虑多个分区
删除超过保留期的日志 可以按完整时间段管理数据 迟到写入、归档和锁等待需要设计

如果大部分请求都只有 call_id，时间分区未必是查询优化的首选。可以先评估普通表的索引和执行计划，再决定是否为数据清理引入分区。分区粒度也应结合保留周期选择：按天保留一年意味着大约 365 个分区，不能只测试当前两三个分区的情况。

本文选择 UTC 日分区，是为了让存储边界不随客户端时区改变。业务按北京时间统计一天时，应先计算该业务日期对应的 UTC 起止时刻，再把两个时间参数传给 SQL。

表结构：把时间边界写清楚

这里的区间包含下界、不包含上界。因此 2025-11-14 00:00:00+00 必须进入下一天的分区。显式写出 +00 可以避免建分区时依赖会话时区。

复合主键里的 started_at 也有意义：PostgreSQL 分区表上的主键或唯一约束必须包含所有分区键列。PRIMARY KEY (id, started_at) 并不单独约束 id 在整个表中唯一；同样，UNIQUE (call_id, started_at) 也不能保证一个 call_id 只出现一次。需要跨日期幂等时，可以另设以 call_id 为唯一键的登记表，并在同一事务里完成登记和日志写入，但要评估这张表的保留策略及额外写入成本。PostgreSQL 分区约束说明

实际接口最好直接传入起止时刻，使用半开区间查询；不要先把时间列转成日期或字符串，再假定优化器会得到相同的裁剪结果。针对最终 SQL 和实际参数检查执行计划，比根据 SQL 外观猜测可靠。

自动建分区和历史清理都需要失败路径

每日执行一次建分区任务，只覆盖今天和明天，无法应对任务连续失败或者历史数据回补。可以按“允许补写的历史窗口 + 未来覆盖窗口”生成分区清单，并让监控检查覆盖到的最晚时刻，而不只是检查任务是否返回成功。

对于这个日志场景，上线前至少需要明确以下行为：

  • 跨日写入：午夜前后持续写入时，下一天的分区必须已就绪。
  • 迟到记录：日志可能在调用发生数小时甚至数天后到达，要约定接受的窗口。
  • 任务并发：只允许一个管理任务执行同一批 DDL，失败后能重试；不能把 IF NOT EXISTS 当成结构校验。
  • 默认分区：如果使用它接住未覆盖日期的数据，需要监控积压并设计迁移流程，避免它长期隐藏建分区故障。
  • 删除边界：只有分区上界不晚于保留截止时刻，才适合整分区清理；包含仍需保留记录的分区不能直接删除。

删除整个分区可以避免逐行删除的工作，但仍涉及锁和依赖关系，不能承诺“永远秒级且不阻塞”。应在演练环境检查长事务、锁等待、归档结果和恢复步骤，再选择直接删除或先分离分区的维护方式。PostgreSQL 分区维护说明

与 MySQL 对比：先比较约束，再做测量

MySQL 8.4 也有分区裁剪，不能用“PostgreSQL 会裁剪，MySQL 会全表扫描”区分两者。应对照各自最终的表结构、条件表达式和执行计划判断。MySQL 分区裁剪文档

MySQL 的唯一键同样受分区键约束：分区表达式中使用的列必须包含在每个唯一键中。因此，把 call_id 的全局幂等约束搬到按时间分区的表时，两边都需要重新审视数据模型。MySQL 分区键与唯一键限制

这篇文章没有同条件的 PostgreSQL/MySQL 对照压测，因此不提供谁更快、谁更适合所有日志系统的结论。若要比较，至少固定以下输入：

输入 应记录的内容
数据集 总行数、行宽、时间跨度、渠道分布和保留周期
表与索引 分区数量、索引定义、唯一约束及统计信息
查询 时间窗口、返回行数、参数、排序与聚合方式
运行条件 数据库版本、CPU、内存、存储、并发及缓存状态
结果 多轮延迟、吞吐、错误、执行计划及维护期间的锁等待

对 AI 调用日志，我会先验证“带时间范围的排查”和“到期数据清理”是否解决了具体问题，再衡量分区管理增加的成本。如果查询多数没有时间条件，或者现有普通表已经满足需求，就没有必要为了分区而迁移。
